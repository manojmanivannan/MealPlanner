# ADR 0004 — Weekly planner redesign (day cards, meal slots, macros, assign/copy modals, states)

- **Status:** Proposed — 2026-08-19. Ready to lock on review of the built planner page (`frontend/dist/index.html`, served by the T2 Vite build). Per the map's plan-first preference, this is a decision + artifact to react to, not a final deliverable.
- **Decides:** GitHub Issue #18 (T4 — Weekly planner redesign)
- **Supersedes:** the legacy single-source `frontend/html/weekly-plan.js` page-content logic as the *built* planner page — claymorphism day-card fills (`meal-card monday` … pastel backgrounds), the `insertAdjacentHTML` assign/detail modals (no focus trap / ESC / aria / scroll lock), the inline `onclick="window.selectRecipeForSlot(...)"` / `window.showRecipeDetails(...)` globals, the silent `console.error` feedback, and the macro contrast failure (`text-stone-500` on the pale-yellow `#fff6b7` full-card fill, which failed AA). The legacy `frontend/html/{index.html,weekly-plan.js}` files stay in place so the current nginx/Docker deployment keeps serving the app until the rollout switches to `frontend/dist/` (per ADR-0002); the build's planner entry no longer imports them.

## Context

T1 (#15) established the token layer, T2 (#16) the Vite MPA + compiled-Tailwind build + shared layout, and T3 (#17) the `.mp-*` component catalog (`modal.js`, `toast.js`, `.mp-card-day`, `.mp-badge-day-soft`, `.mp-state`, `.mp-skeleton`, `.mp-btn`, `.mp-check`, `.mp-input`) with the explicit follow-up that "T4 (#18) … adopt these classes and swap their `insertAdjacentHTML` modals for `modal.js` and their `alert()`/`console.error` for `toast.js`." This ticket is that adoption for the planner.

The grilling brief (#14) decided the planner UX wins: 5 plannable slots (Sides/Weekend Prep are hub-only), feedback states + quick-remove + copy-day + a smarter assign modal, **defer drag-and-drop**, desktop-primary with mobile stacking to one-day-per-row. The macro display must be readable (AA), the assign modal must be real (search + multi-select + recently-used/favorites pinned), and the PDF export (`/api/weekly-plan/pdf`) must keep working. "Use components from T3," then lock.

## Decision

Replace the built planner page with a token-driven module (`frontend/src/pages/weekly-planner.js`) that consumes the T3 catalog directly and drops the legacy single-source import. The legacy CDN page (`frontend/html/`) is left untouched for deployment continuity. The system is:

- **Page entry is now the page-content logic.** `frontend/src/pages/weekly-planner.js` no longer `import`s `../../html/weekly-plan.js`; it owns the whole planner (state, fetch, render, actions, modals, PDF export) and imports `mountLayout` + `openModal` + `toast`. `frontend/index.html` is a bare skeleton (header placeholder, a title/subtitle/Export-PDF toolbar, and `#meal-plan-grid`); all dynamic markup is rendered into the grid by the module. The PDF-export handler moved off the old inline `<script>` into the module (it already had been, in T2) and its `alert()`/`console.error` became `toast.warning`/`toast.error` with a `data-loading` spinner on the button.

- **Day cards — neutral surface + day accent, never a full-card day fill.** Each day is an `.mp-card.mp-card-day` (3px top border) with `--day-color`/`--day-fg`/`--day-soft` set inline to the T1 day tokens (`var(--day-mon)` …). The header carries a `.day-dot`, the day name, a `.mp-badge-day-soft` "planned/total" count, and a **Copy** ghost button. The day color is the border/dot/badge only — the background is the neutral surface — so the locked T1 contract (day color never as text/background) holds and the old yellow-contrast failure is structurally gone.

- **5 meal slots per day.** `pre_breakfast / breakfast / lunch / snack / dinner` (chronological; Sides/Weekend Prep excluded as hub-only). Each slot row: a label + a **Clear** (occupied only) + an **Add/Change** button, the assigned recipes as removable chips, and a per-meal macro row. The slot filter logic is preserved verbatim from the legacy code (pre_breakfast and snack are meal-type-scoped; the other three accept any non-`pre_breakfast`/`snack` recipe) — this is a *redesign of look + UX*, not a change to the data rules, so `sides`/`weekend_prep` recipes still surface in the three main meals exactly as before (out of scope to change here).

- **Macros at AA contrast.** Per-meal and per-day macro rows render `E / Pr / Ca / Fa / Fb` (energy/protein/carbs/fat/fiber) in tabular numerals (`.tnum`) with `text-muted`/`text-secondary` on the neutral surface — the failing `text-stone-500`-on-pastel is gone. Per-serving values use the existing `macro / serves` convention. The day-total row sits in the card footer behind a top border.

- **Assign modal — accessible, with search + multi-select + recent pinning.** Built on `modal.js` (focus trap, ESC, aria-labelledby/describedby, body-scroll lock, focus restore, full-screen on mobile). Body is a search `.mp-input` + a scrollable list of `.mp-check` checkboxes (multi-select, pre-checked with the slot's current recipes). Recipes the user has assigned recently (an MRU list in `localStorage` under `mp-planner-recent`, capped at 6) are pinned into a **Recently used** group above **All recipes**. Live search hides non-matching items and collapses any group that empties. Save collects the checked ids, pushes them to recent, closes via `ctrl.close()` (so focus/scroll are restored — never removed by hand), and PUTs the slot. This replaces the `insertAdjacentHTML` modal that had no trap/ESC/aria and used `onclick` globals.

- **Inline quick-remove + clear-slot + copy-day.** Each recipe chip has a compact × (reusing the T3 `.mp-toast-close` small-dismiss affordance — see Consequences) that PUTs the slot minus that recipe. **Clear** empties a slot. **Copy** opens a small modal listing the other six days as `.mp-check` checkboxes (each with its day-dot); the **Copy** button is disabled until at least one target is checked, then PUTs every meal slot from the source day into each target (overwrite semantics) in parallel and re-fetches. All three are driven by a **single event-delegation handler** on the grid keyed on `data-action`/`data-day`/`data-meal`/`data-recipe-id` — the legacy inline `onclick="window...."` globals are gone.

- **Recipe detail modal.** The old `insertAdjacentHTML` detail modal is replaced by `openModal`: meal-type/serves/vegetarian badges, escaped ingredients + instructions (`whitespace-pre-line`), and a per-serving macro row. The modal title (recipe name) is set via `textContent` by `modal.js`, so it is XSS-safe; all other reflected recipe fields pass through an `esc()` helper before innerHTML — the one place the modal.js "trusted markup" assumption does not hold (recipe fields are user-authored).

- **Loading / empty / error states.** Loading renders seven shimmering `.mp-skeleton` day cards (no layout jump). A fetch failure renders an `.mp-state-error` with a **Retry** button (re-runs the load). When the user has no recipes at all, an `.mp-state` empty card points to the Recipe Hub. Failures are never silent (`console.error`) or blocking (`alert()`) — recoverable surfaces replace blank space, and feedback is `toast.*`.

- **PDF export preserved.** `/api/weekly-plan/pdf` is unchanged on the backend; the client still fetches the blob and triggers a download, now with a loading spinner on the button and `toast` feedback instead of `alert()`.

## Consequences

- **Positive:** The planner's two worst gaps from the grilling brief (silent `console.error`/`alert()` feedback and `insertAdjacentHTML` modals with no a11y) are replaced by the reusable T3 `toast.js`/`modal.js`; the macro contrast failure is fixed by construction (neutral surface + token text, day color as accent only); quick-remove / clear-slot / copy-day and a real search+multi-select+recent assign modal land in one place; the legacy inline-`onclick` globals are gone, replaced by one event-delegation handler; states (loading/empty/error) replace blank failures. Everything is token-driven, so light/dark + the manual toggle work without per-component overrides.
- **Negative:** During rollout the legacy `frontend/html/weekly-plan.js` (served by nginx) and this new module (served by `frontend/dist/`) coexist and diverge — the deployed app keeps the old planner until the `frontend/Dockerfile` + nginx root switches to `dist/` (the map's deferred rollout item). The `.mp-toast-close` class is reused as the in-chip compact dismiss affordance rather than minting a new `.mp-chip-remove` component class — T3 is locked, so reusing the existing small-dismiss styling avoids reopening the catalog for one new class; it is a minor semantic stretch (a non-toast button carries a `toast`-named class) documented here and in a code comment. The recipe-slot filter still surfaces `sides`/`weekend_prep` recipes in the three main meals (preserved legacy behavior); tightening that is out of scope for a look/UX redesign and is noted for a future data-rules ticket if desired.
- **Follow-ups:** T5 (#19 recipe hub), T6 (#20 ingredients), T7 (#21 shopping list) adopt the same `modal.js`/`toast.js` swap; once all four land, `legacy.css` + the clay classes and the legacy `frontend/html/*.js` page-content files can be removed and the rollout switches `frontend/Dockerfile` + nginx to `frontend/dist/`. **Automated a11y/keyboard + responsive verification is deferred to T8 (#22, the audit gate)** — consistent with the T1/T2/T3 precedent (build + manual inspection), since the frontend still has no JS test runner / browser automation harness.
- **Blocked-by:** #15 (T1 tokens), #16 (T2 build), #17 (T3 catalog — `modal.js`/`toast.js`/`.mp-*`). **Blocks:** #22 (T8 audit) for the planner page.

## Verification

`npm run build` (in `frontend/`) produces `frontend/dist/`:

- `index.html` references only hashed `/assets/*` (`index-*.js`, `bootstrap-*.js`/`layout-*.js`/`toast-*.js`, `bootstrap-*.css`) — no `cdn.tailwindcss.com`, no `fonts.googleapis.com` (confirmed by grep of `dist/`).
- The built planner entry bundle (`index-*.js`) grew to ~16 kB (it now bundles `modal.js` + `toast.js` + the page logic instead of re-importing the legacy file); `toast.js` splits out as a shared chunk (also used by the catalog). No `clay-` / `meal-card` / `insertAdjacentHTML` / inline `onclick=` strings remain in the built planner entry (confirmed by grep).
- The compiled CSS contains every `.mp-*` class the module emits (`.mp-card-day`, `.mp-badge-day-soft`, `.mp-state`, `.mp-modal`, `.mp-btn`, `.mp-skeleton`, `.mp-check`, `.mp-input`) resolving to T1 variables, plus the generated `divide-line-subtle` utility, so light/dark + the manual toggle drive the planner at runtime. The `/weekly-plan/pdf` route reference is present in the built entry.
- `node --check` parses the module; `npm run dev` serves `index.html` and every module (`src/pages/weekly-planner.js`, `src/components/modal.js`, `src/components/toast.js`, `design/components.css`, `design/tokens.css`) at 200.

**Scope note on the test suite:** as with T1–T3, the repo's test suite is the Python/pytest backend stack (`tests/`, needs `pytest` + `fastapi.testclient` + testcontainers Postgres/Docker), which is not installed here and has zero overlap with these frontend-only changes — so it was not re-run. The backend `/weekly-plan` and `/weekly-plan/pdf` routes are unchanged. The frontend has no JS test runner yet; automated a11y/keyboard/responsive verification is the T8 gate ticket's job.
