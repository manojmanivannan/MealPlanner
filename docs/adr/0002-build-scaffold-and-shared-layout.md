# ADR 0002 — Build scaffold & shared layout (Vite MPA, compiled Tailwind v4, JS-injected header/auth)

- **Status:** Proposed — 2026-08-18. Ready to lock on review of the vertical slice (`frontend/` Vite build, demonstrated across the authed page set — planner, recipe hub, ingredients — plus the welcome auth-gate). Per the map's plan-first preference, this is a decision + artifact to react to, not a final deliverable.
- **Decides:** GitHub Issue #16 (T2 — Build scaffold + shared layout)
- **Supersedes:** the runtime Tailwind CDN + the per-page `<header>` + auth `<script>` + ~230-line `<style>` block duplicated across `frontend/html/`'s authed pages. The new build now covers all three authed pages plus `welcome`; `frontend/html/` stays in place only so the current nginx/Docker deployment keeps serving the app until the rollout switches to `frontend/dist/`.

## Context

The frontend is a vanilla multi-page app served by nginx (`frontend/html/` → `/usr/share/nginx/html`), with a FastAPI backend at `/api`. Today every authed page carries three pieces of copy-pasted boilerplate: (1) a runtime Tailwind CDN `<script src="https://cdn.tailwindcss.com">` — a production anti-pattern (JIT-in-the-browser, FOUC, external dependency, can't be CSP-pinned); (2) a ~230-line `<style>` block of claymorphism card styles, identical across `index.html`, `recipe-hub.html`, `ingredients.html` (and a smaller variant on `welcome.html`); and (3) an identical `<header>` + auth IIFE that checks the bearer token, redirects to `welcome.html` on failure, fetches `/api/auth/me`, and wires the user dropdown + logout. A shared `styles.css` exists but is commented out. T1 (#15) established the design-token layer (`frontend/design/tokens.css`) as the source of truth for a crisp/flat, dark-mode, AA-contrast identity; it explicitly leaves the wiring into the compiled Tailwind v4 `@theme` layer to T2.

The grilling brief (Wayfinder map, #14) decided: stay multi-page (no SPA/framework migration), Vite + compiled Tailwind v4 + a token layer, JS-injected shared component. Issue #16 mandated confirming the current (2026) Vite MPA + Tailwind v4 patterns before implementing — external knowledge, looked up rather than guessed.

## Decision

Adopt a Vite MPA build under `frontend/` with compiled Tailwind v4 and a JS-injected shared layout, demonstrated across the authed page set. The system is:

- **Vite MPA + first-party Tailwind v4 plugin.** `vite.config.js` registers `@tailwindcss/vite`, sets `appType: 'mpa'` (each `.html` served directly, no SPA history fallback), and lists each page's HTML as a `build.rollupOptions.input` entry (`fileURLToPath(new URL('./<page>.html', import.meta.url))` for ESM-safe paths). The stylesheet is `@import "tailwindcss"` — CSS-first, no `tailwind.config.js`, no `content` array (v4 auto-detects sources). No runtime CDN. The dev server proxies `/api` to the backend with `rewrite: (path) => path.replace(/^\/api/, '')`, mirroring nginx's `location /api/ { proxy_pass http://backend:5000/; }` (the FastAPI routers mount at `/auth`, `/recipes`, `/weekly-plan`, `/ingredients` with no `/api` root, so the prefix must be stripped in dev too).
- **T1 tokens bridged via `@theme inline`.** `src/styles.css` imports the canonical `../design/tokens.css`, then maps its semantic variables onto Tailwind utility namespaces with `@theme inline`: `--color-surface: var(--bg-surface)`, `--color-accent: var(--accent)`, `--color-line: var(--border-default)`, `--font-sans: var(--font-sans)`, `--radius-*: var(--radius-*)`, … `inline` makes each utility resolve the T1 variable *directly* (`.bg-surface { background: var(--bg-surface) }`) rather than copying a static value, so the utilities follow the runtime light/dark switch defined in tokens.css (system `@media (prefers-color-scheme: dark)` + manual `[data-theme]`). Border tokens are exposed as `--color-line*` so the utility reads `border-line` rather than the redundant `border-border-default`. T1's `--color-danger/success/warning` already occupy the `--color-*` namespace as raw variables, so they are left un-mapped and consumed via arbitrary values where needed (e.g. `text-[var(--color-danger)]`).
- **Legacy clay styles centralized, not yet replaced.** The ~230-line block is lifted verbatim into one `src/legacy.css` (shared across all pages via the build), so page-content JS that injects `.meal-card` / `.clay-*` / `.day-bg-*` markup still renders unchanged. The broad `!important` radius/shadow overrides (`.rounded-lg, .rounded-md { border-radius: 18px !important }`, `.shadow-md { … !important }`) — which would have polluted the new token-driven header's utilities — are removed; cards keep their own explicit radius/shadow, and images round via a plain `img { border-radius: 12px }`. T3 (#17, component catalog) replaces `legacy.css` with token-driven component classes; this ticket deliberately does not.
- **Self-hosted Inter.** `@fontsource/inter` (400/500/600/700) imported by the shared `src/bootstrap.js` — `@font-face` is emitted into the compiled CSS and the font files are hashed assets, with no request to `fonts.googleapis.com`. Matches the T1 swatch's stated intent ("the real build (T2) ships Inter via Vite/Tailwind") and the "compiled, no runtime CDN" direction.
- **JS-injected shared layout.** `src/layout.js` exports `mountLayout({ activeNav })`, which injects a token-driven nav header into a `<div id="app-header">` placeholder on the page and runs the auth bootstrap (token check → `welcome.html` redirect; `/api/auth/me` → email; dropdown toggle with `aria-expanded`; logout). This single module replaces the per-page `<header>` + auth IIFE. The active nav link is parameterized per page (`planner` | `recipes` | `ingredients`). `src/bootstrap.js` centralizes the self-hosted fonts + compiled stylesheet + the layout re-export, so each authed page entry is just: import bootstrap, call `mountLayout`, import the page-content logic.
- **Vertical slice across the authed set.** All three authed pages — `index.html` (Weekly Planner), `recipe-hub.html`, `ingredients.html` — plus the `welcome.html` auth-gate are converted to the build. Each has a bare `<head>` (no CDN, no inline `<style>`, no font `<link>`) and a `<div id="app-header">` placeholder; the three authed pages call `mountLayout({ activeNav })` then import their existing page-content logic single-source (`frontend/html/weekly-plan.js` / `recipe-hub.js` / `ingredients.js`); the PDF-export handler moved off its inline `<script>` into the planner entry. `welcome` boots the shared stylesheet but mounts no header (it's pre-auth). The current `frontend/Dockerfile` + nginx root still serve `frontend/html/`, so the deployed app is unchanged.

## Consequences

- **Positive:** One compiled CSS artifact per build — no runtime JIT CDN (faster, no FOUC, CSP-friendly, works offline); tokens drive utilities *and* respond to dark mode by construction (the `@theme inline` bridge is the mechanism); header + auth duplication is eliminated at a single source across all three authed pages; the legacy pages keep working unchanged (nginx still serves `frontend/html/`), so the rollout is reversible.
- **Negative:** During rollout the legacy `frontend/html/` and the new `frontend/dist/` coexist (both contain all authed pages) — the deployed app keeps serving `frontend/html/` until `frontend/Dockerfile` + nginx switch to `frontend/dist/`. Self-hosted fonts add bundle weight (offset by dropping the external request). The `@theme inline` semantics are subtle — a future maintainer must understand that `inline` inlines the *variable reference*, not the value, which is what makes dark mode work.
- **Follow-ups:** Switch `frontend/Dockerfile` + nginx root to serve `frontend/dist/` (and drop the now-redundant `frontend/html/`) — this is the map's "Deployment/rollout phasing" item, explicitly deferred; T3 (#17) consumes the tokens and replaces `legacy.css` with token-driven component classes (the page-content JS in `frontend/html/*.js` is reused single-source and inherits the new component classes as they land).
- **Blocked-by:** #15 (T1 tokens — consumed by the `@theme inline` bridge). **Blocks:** #17 (T3 component catalog — needs the build to render components).

## Verification

`npm run build` (in `frontend/`) produces `frontend/dist/`:

- All four pages — `index.html`, `recipe-hub.html`, `ingredients.html`, `welcome.html` — build as separate `rollupOptions.input` entries sharing a common `bootstrap` CSS/JS chunk and a shared `layout.js` chunk; each `dist/*.html` references only hashed `/assets/*` (no `cdn.tailwindcss.com`, no `fonts.googleapis.com` / `fonts.gstatic.com`).
- The nav links (`recipe-hub.html`, `ingredients.html`) and the auth-redirect target (`welcome.html`) all resolve to built pages, so there is no dead nav and no SPA-fallback redirect loop (`appType: 'mpa'` also prevents the latter for any genuinely-missing route).
- The compiled CSS contains the token utilities resolving to T1 variables — `.bg-surface { … var(--bg-surface) }`, `.text-accent { … var(--accent) }`, `.border-line { … var(--border-default) }`, `.font-sans { … var(--font-sans) }` — so utilities switch at runtime.
- Both dark blocks survive (Lightning CSS minifies the media query to `prefers-color-scheme:dark)` and the toggle selectors to `[data-theme=dark]` / `[data-theme=light])`): all T1 dark values (`--bg-canvas:#14171f`, `--bg-surface:#1c2030`, `--accent:#2dd4bf`, …) are present, so system + manual dark mode both work.
- The compiled CSS retains the legacy clay classes (`.meal-card`, `.clay-btn`, `.clay-section`, `.day-bg-monday`, `.hub-tab`, `.clay-title`), so the reused page-content JS renders unchanged.
- `@font-face` for Inter is emitted into the compiled CSS; the woff/woff2 files are hashed assets under `dist/assets/`.

**2026 patterns confirmed (not guessed):** Vite MPA via `build.rollupOptions.input` as an object of resolved HTML paths (ESM configs use `fileURLToPath(new URL('./x.html', import.meta.url))`); Tailwind v4 via the first-party `@tailwindcss/vite` plugin with `@import "tailwindcss"` + `@theme` / `@theme inline` (CSS-first, no JS config, automatic content detection). Sources: [Installing Tailwind with Vite](https://tailwindcss.com/docs/installation/using-vite), [Theme variables](https://tailwindcss.com/docs/theme), [Vite multi-page build guide](https://vite.dev/guide/build).
